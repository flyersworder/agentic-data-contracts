\section{The Instrument}
\label{sec:system}

\texttt{agentic-data-contracts} is an open-source Python library that loads a
data contract and exposes a database to an agent through nine governed
tools. The library is the instrument, not the contribution: the hollow arm
runs the identical library, tools and rules with the prose removed, and the
text arms put the same contract in the prompt over plain tools.

\subsection{The contract}
\label{sec:contract}

A contract is two YAML files. \texttt{contract.yml} declares the tables the
agent may read, the operations it may not issue (\texttt{DELETE},
\texttt{DROP}, \texttt{UPDATE}, \texttt{INSERT}, \texttt{CREATE},
\texttt{ALTER} and five more), and the domains, each with a summary and a
prose description. \texttt{semantic.yml} declares the metrics, each with a
description and an executable \texttt{sql\_expression} (from library version 0.62, a
metric may declare the join it spans), the tables with a description per
column, and the relationships. The DABStep contract is 60{,}181 characters
with 14 metrics; Figure~\ref{fig:contract} shows one, as it appears in the
contract and in its hollow counterpart. The same files supply the semantics
the agent reads and the rules the tool layer enforces.

\subsection{Nine tools and two-layer validation}
\label{sec:tools}

{\sloppy The tools fall into three groups. Four discover structure:
\texttt{describe\_table}, \texttt{preview\_table},
\texttt{lookup\_relationships} and \texttt{list\_metrics}. Three deliver
semantics: \texttt{lookup\_domain} returns a domain's prose,
\texttt{lookup\_metric} a metric's description and SQL expression, and
\texttt{trace\_metric\_impacts} the metrics that depend on a table. Two
handle queries: \texttt{inspect\_query} validates a statement and returns
either a pass or a reason, and \texttt{run\_query} validates and executes
it. Validation is two-layer. Every statement is parsed with
sqlglot~\cite{sqlglot} and checked statically against the table allow-list
and the forbidden operations; where a database adapter is available, a dry
run follows. A rejected statement returns its reason to the model rather
than an error to the user. The tool descriptions themselves carry 3{,}042
characters of procedural text (\texttt{inspect\_query} tells the model to
call \texttt{lookup\_metric} first), and that text is part of what the
hollow arm holds fixed.\par}

\subsection{The hollow contract}
\label{sec:hollow}

The hollow contract is generated from the frozen one by a script, so the
only difference is the one the generator makes, auditable as a diff.
Emptied: domain prose, metric descriptions, every \texttt{sql\_expression}
and all column and relationship descriptions. Retained byte for byte:
every name, type and structure, the table allow-list, the forbidden
operations and the nine tools. A lookup against it returns \emph{``No
documentation is available for this domain.''} The test suite asserts that
no 6-gram of \texttt{manual.md} survives into it while the real contract
shares 6-grams with the manual, and the transcripts confirm the loop ran:
on \mGLM{} the hollow arm called \texttt{lookup\_domain} on 272 of 401
tasks. Prompt length is not held constant (1{,}984 characters against
2{,}475): text that reads as content but carries none would be a different
treatment, not a cleaner control.

\subsection{Three ways to author a contract}
\label{sec:authoring-paths}

\textbf{By hand.} The DABStep contract was written in one session on
2026-08-30 from \texttt{manual.md}, the dataset README and the data. A
design rule fixed that morning, before any gold existed, barred consulting
any question, gold or score while authoring. The golds were reconstructed
about an hour before the first freeze, into a file kept outside the
repository; the freeze commit records that none was read. Three re-freezes
followed before any score existed, each justified from the two documents.
The contract states two facts the manual does not
(Section~\ref{sec:delivery}), both present in the first freeze and never
edited. That the data stores ``all'' as an empty list was taken from the
data and marked as an interpretation. That overlapping fee rules each
apply was not marked: the definition sums over a join of each
transaction to ``the fee rule that matches it'', the ordinary
join-and-sum idiom, which reads as a convention written without noticing
it was one rather than a decision informed by the golds. We can show the
order and the rules; we cannot prove from outside that they were kept.

\textbf{Compiled.} The compiler (\texttt{dce.compile}) turns a manual or KB
into a contract entry by entry. For each entry a model writes a definition,
checks its SQL against the database read-only, and either emits it or
refuses it with a reason; refused entries keep their text. It translates
the documentation rather than extending it: on LiveSQLBench every one of
the 1{,}369 KB definitions appears verbatim in the compiled contracts. We use
Sonnet~5 and Opus~5.5 as compiler models, with and without declared joins.

\textbf{Authored.} The author (\texttt{dce.author}) is one model session
per database that reads the whole KB, explores the data read-only, writes
the whole contract, and maps every KB entry to where the contract holds
it. It sees no task, question, gold or result. A checker compares its
definitions with reference implementations where those exist
(experiments 4 and 4b).
