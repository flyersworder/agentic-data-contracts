\section{Governance}
\label{sec:governance}

The contract under test declares forbidden operations as well as semantics, and
the tool layer enforces them. Because the same runs that measure accuracy also
record every statement the agent submitted and a post-run integrity check on
the database, a second result falls out of the same 3{,}208 transcripts at no
additional cost.

\subsection{144 mutation attempts, all in ungoverned arms}

We counted mutating statements the model actually \emph{submitted} to a SQL
tool --- \texttt{CREATE TABLE}/\texttt{VIEW}, \texttt{DROP}, \texttt{INSERT},
\texttt{UPDATE}, \texttt{DELETE}, \texttt{ALTER}, \texttt{TRUNCATE} at a
statement position in the query argument.

\textbf{144 mutating statements across 24 tasks in the ungoverned arms; zero in
either governed arm, on either model.} Run~B alone gives $p{=}0.13$ --- it is
underpowered here as elsewhere --- so the result rests on run~A and the pooling.

\subsection{Deterrence, not interception}

A rejected tool call still appears in the transcript as a tool call: the count
above is of what the model \emph{emitted}, not what survived validation. Zero
therefore does not mean ``attempted and blocked'' --- it means \textbf{never
attempted}. The forbidden-operation rules, stated declaratively in the contract
and visible in the system prompt, deterred the behaviour rather than
intercepting it.

That is a cheaper mechanism than enforcement and a more fragile one: it costs
nothing at query time and depends on the model's compliance rather than on the
validator. Our data cannot distinguish a model that will not attempt from one
that would be caught if it did --- both produce zero. We report what the
transcripts support: with the rules present, the attempts stop.

\subsection{One escalation reached the database}

The post-run integrity check flagged exactly one row in 3{,}208: task~68,
\armS{}, run~B. It is 1 of the 24 attempting tasks because DuckDB \texttt{TEMP}
tables die with the connection; only this run escalated to persistent tables.

The escalation was deliberate, and the model narrates it. It first issued
\texttt{CREATE TEMP TABLE feats}, and on the next call received \texttt{Table
with name feats does not exist!}. Its reasoning:

\begin{quote}\small\itshape
``TEMP table per session? The previous CREATE TEMP TABLE in the same connection.
The tool might use separate connections per call, so temp tables don't persist.
Let me create a regular table\ldots''
\end{quote}

and, having established that they now persist, \emph{``Since tables persist
across calls (non-temp), I can do sequential UPDATE operations.''} It then
hand-rolled Gaussian elimination across twelve statements ---
\texttt{DROP TABLE IF EXISTS m1; CREATE TABLE m1 AS \ldots} through \texttt{m6}
--- to solve a linear system, and answered the question wrongly as well.

The shape is what makes this worth reporting. It is not an injection, a
jailbreak, or an adversarial prompt, but a competent agent routing around a
session boundary to finish its work, in which every individual statement is
locally reasonable. No test written in advance would have anticipated this path,
which is the argument for a declarative rule that does not need to. The run used
a disposable per-worker copy, so nothing real was harmed, and the integrity
check reported clean, so the detection is trustworthy.

\textbf{One corruption event is an anecdote, not a rate.} The defensible number
is the 144 attempts, and the defensible claim is about attempt frequency under
declared rules, not about how often attempts become damage.
